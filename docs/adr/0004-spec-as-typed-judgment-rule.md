# ADR 0004: 规格串必须解析为带类型的判定规则，且解析失败要报错而非猜

- **状态**: 已接受
- **日期**: 2026-08-14

## 背景

规格（spec）是这个系统的**领域核心**：判定合格与否、不良率、报告结论，全部由它决定。
1.0 版对它的处理是——每次判定时用正则把非数字字符剥掉：

```js
// server.js calculateJudgment() 与 seed-real-data.js judge() 各写了一份
const limit = parseFloat(s.replace(/[^0-9.]/g, ''));
```

这段代码有两个独立的严重问题。

### 问题一：单位里带数字的规格会被静默解析错

线材领域的截面积单位就是 `mm2`（平方毫米），产品型号里到处都是（RV-**0.5**、BV-**2.5**）。
一旦有人把规格写成带 `mm2` 的形式：

| 规格串 | 剥离后 | 解析出的阈值 | 正确阈值 |
|---|---|---|---|
| `≥1.5mm2` | `1.52` | **1.52** | 1.5 |
| `≤2.5mm2` | `2.52` | **2.52** | 2.5 |
| `≥10^8Ω` | `108` | **108** | 1×10⁸ |
| `8.4±0.4mm2` | ± 分支 → `0.42` | 公差 **0.42** | 0.4 |

它**不报错、不警告**，只是安静地用一个错阈值去判合格与不合格。
对一个质检系统来说，「静默给出错误判定」是最坏的一类故障——
数据看着完全正常，报告照样生成，签名照样签，错误一路流到客户手里。

**这个风险的准确范围（已实测，不要夸大）：**

用旧解析器逐条核对 `seed-real-data.js` 里现有的 52 条真实规格串，
结果是 **0 条被读错**。也就是说：地雷已经埋好，但当前数据还没踩上。

之所以仍把它列为最高优先级，是因为**踩中的概率不低**：

| 写法 | 旧解析器读出的阈值 | 正确阈值 | 这个写法有多常见 |
|---|---|---|---|
| `≥1.5mm2` | **1.52** | 1.5 | 截面积的标准单位；本库产品名写的就是 `0.5mm2` / `3x1.5mm2` / `3G1.0mm2` |
| `≥1.5 mm2`（带空格） | **1.52** | 1.5 | 同上 |
| `≥10^8Ω` | **108** | 10⁸ | 绝缘电阻的常规量级写法 |
| `≥1×10^8Ω` | **1108** | 10⁸ | 同上 |
| `2.5mm2±0.1` | 公差 **2.52** | 应判为无法解析 | 顺序颠倒的手写形式 |

同一个数据库里，产品名称字段已经在用 `mm2` 这种写法了。
换句话说：不是「系统今天在出错」，而是「下一个按本库既有习惯录截面积规格的人，
会拿到一个不报错的错判」。这个区别很重要，但不改变结论 —— 判定是这个系统的心脏，
不能留一处「输入合法、结果错误、全程静默」的路径。

### 问题二：同一规则实现了两份

`server.js` 的 `calculateJudgment()` 和 `seed-real-data.js` 的 `judge()` 是同一套逻辑的两份拷贝。
改一处不会同步另一处。现在两份还基本一致，纯属运气。

## 决策

**一、规格在进入系统的边界处一次性解析成带类型的判定规则，之后系统内部不再见到裸字符串。**

```ts
type JudgmentRule =
  | { kind: 'max';         limit: number; unit: string }   // ≤0.5Ω
  | { kind: 'min';         limit: number; unit: string }   // ≥1500V
  | { kind: 'tolerance';   center: number; tolerance: number; unit: string } // 2.8±0.2mm
  | { kind: 'range';       lower: number; upper: number; unit: string }      // 5.0~5.5mm
  | { kind: 'qualitative'; expected: string };             // 合格 / 通过
```

**二、解析器显式区分「比较符 / 数值 / 单位」三段，绝不用剥字符的方式取数。**
数值部分只允许匹配 `-?\d+(\.\d+)?`，紧跟其后的剩余部分整体视为单位。
这样 `≥1.5mm2` 会正确得到 `limit: 1.5, unit: 'mm2'`。

**三、解析失败必须显式失败，不许回退到猜测。**
返回 `Result<JudgmentRule, ParseError>`（或抛出），由调用方决定如何处理。
在 UI 上表现为：该测试项标记为「规格无法识别」并**拒绝自动判定**，要求人工确认。
宁可让人看到「我不认识这个规格」，也不能让人看到一个错误的「合格」。

**四、判定逻辑是唯一一份纯函数模块，有测试。**
测试夹具直接用现有 52 个真实规格串（来自 `seed-real-data.js` 的测试模板），
逐条断言解析结果与判定结果。新增规格形态时先加夹具再改解析器。

**五、单位段必须校验，含指数记号的一律拒绝。**
原型阶段实测发现：只做「数值 + 剩余部分即单位」的切分仍不够 ——
`≥10^8Ω` 会被解析成 `limit: 10, unit: '^8Ω'`。虽然比旧版的 `108` 好，但仍是错的。
因此解析器还需一条规则：**单位段若以 `^`、`e`、`E`、`×`、`*` 开头（疑似指数记号），判为 unparseable**。
这条必须作为实现阶段的测试用例写进夹具。

## 原型阶段的实测验证

在 `prototype/ledger-ui.PROTOTYPE.html` 中实现了本 ADR 的解析器，并对真实数据做了断言：

```
[OK] 全部 29 种真实规格形态均正确解析
[OK] 11 条判定断言全部通过（含 3 条真实不合格项 + 「0 是合法值」回归）

=== 对照实验：规格 ≥1.5mm2，实测值 1.51 / 1.52 / 1.53 ===
  旧解析器: 不合格   (阈值被读成 1.52)  ← 错判，且不报错
  新解析器: 合格     (阈值 1.5, 单位 mm2)
```

准确的结论有两层，不要混为一谈：

1. **对现有 52 条规格**，旧实现给出的判定是对的（已逐条核对，0 条读错）。
   所以这不是一份「线上正在错」的事故报告。
2. **对 `mm2` / `10^8` 这类写法**，旧实现会静默给出错误判定 —— 上面是可运行代码跑出的对照结果，
   不是推测。而这类写法在本领域（以及本库自己的产品名里）是常规写法。

本 ADR 要消除的是第 2 层：一条「输入合法、结果错误、全程无声」的路径。

## 后果

**得到**
- 消灭了「单位含数字 → 静默错判」这类质检系统最不能有的故障
- 判定规则只有一份实现、一套测试，改动有唯一入口
- 未解决的规格形态会被暴露出来而不是被掩盖

**付出**
- 比一行正则复杂得多，需要一个真正的解析模块
- 存量数据里若有解析不了的规格串，会在迁移时集中暴露（这是好事，但要有处理流程）
- 调用方必须处理解析失败分支，不能假装它不存在

## 备选方案

- **在正则里补上单位白名单**：能缓解，但每出现一个新单位就要改一次代码，且仍是猜测式解析。
- **规格改为结构化录入（三个字段：比较符 / 数值 / 单位）**：从根上消除解析问题，
  但要求用户改变录入习惯，且存量 52 条模板需要迁移。
  **保留为后续演进方向**——本次先做能正确解析字符串的解析器，
  并把它作为结构化录入的迁移工具。
