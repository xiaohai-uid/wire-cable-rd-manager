# SPEC: 线材研发管理系统 2.0 — 质量优先的核心闭环

- **状态**: 待实现
- **日期**: 2026-08-14
- **上游决策**: ADR 0002（现代栈 + 双适配器）、ADR 0003（网格优先录入）、ADR 0004（规格→带类型判定规则）
- **原型来源**: `prototype/ledger-ui.PROTOTYPE.html` 变体 C 胜出（质量热力图）
- **术语**: 全文使用 `CONTEXT.md` 的领域术语表词汇

## Problem Statement

我是线材厂的研发工程师。我每天要做两件事：**把打样批次的测试数据录进去**，
和**回答「现在哪里有问题」**。

1.0 版把这两件事都做得很别扭：

**录数据像在受刑。** 一个 RVV-3x1.5 批次有 12 个测试项，每项要填三次测量值。
系统让我一项一项地开模态框、填三个数、保存、再开下一个 —— 一个批次 12 次往返、36 个数值。
我手上的原始记录本身就是一张二维表（测试项 × 三次测量），我只想把它照抄进去，
但系统硬要把它拆成 12 次对话。

**看质量全貌根本看不到。** 首页给我四个大数字（产品数、记录数、不合格数、不良率），
但这四个数字回答不了我真正的问题：**是哪个产品的哪个测试项在出问题？**
是 SYV 的回波损耗一直不行，还是 BV 的老化测试偶发？我只能进台账页翻 62 条记录自己找。
更糟的是趋势图上的不良率一直显示 0 —— 那个数字是硬编码的。

**我不信任它的判定。** 判定逻辑靠「把规格串里的非数字字符全剥掉，剩下的当阈值」。
我不知道它什么时候会读错，也不会有任何提示。对一份要签名的质检报告来说，这不可接受。

**它看起来像个模板。** 靛蓝渐变导航条、四个统计卡、每点一下就整页跳转。
它不像我的工作台，像一个交付物。

## Solution

把首页从「四个大数字」换成**质量热力图**：一张 `测试项 × 产品` 的矩阵，
每个格子是那个组合的不良率，颜色深浅就是严重程度。我一眼就能看到
「SYV-75-5 的回波损耗那一格是红的」，而不需要读任何数字。

点那个格子，**在同一页展开**该组合的全部测试台账记录 —— 三次测量值、平均值、判定、批号、日期。
不合格的那次测量单独标红（不是整行含糊标红）。不跳页。

要录数据时，从明细里进入**批次录入网格**：选定产品和批号后，测试模板决定网格铺出多少行，
每行是一个测试项和它的规格，右边三列是三次测量。像用电子表格一样用 Tab / Enter / 方向键走位，
支持从 Excel 直接粘贴一整块。每填完一行立刻显示判定，整批一次性保存。

判定由**唯一一份纯函数判定引擎**给出。规格串在进入系统时就被解析成带类型的判定规则；
解析不了的规格会明确显示「规格无法识别，拒绝自动判定」，绝不猜。

同一套界面有两种数据来源：本地跑的时候连 SQLite 真实落盘干活；
在线 demo 用内存适配器带真实种子数据，点开链接就能试，界面上明确标注「演示模式」。

## User Stories

### 质量全貌（热力图首页）

1. 作为研发工程师，我想在打开系统的第一屏就看到 `测试项 × 产品` 的不良率矩阵，以便不用读数字就知道问题集中在哪。
2. 作为研发工程师，我想让矩阵格子的颜色深浅表示不良率高低，以便用余光扫一眼就能定位异常。
3. 作为研发工程师，我想让「该产品没有这个测试项」和「有这个测试项但零不合格」在视觉上明显不同，以便不把「没测」误读成「测了没问题」。
4. 作为研发工程师，我想看到每个格子的实际分母（测了多少次），以便判断 100% 不良率是「1/1」还是「12/12」——这两者严重程度完全不同。
5. 作为研发工程师，我想让矩阵的行按整体不良率降序排列，以便最该处理的测试项浮到最上面。
6. 作为研发工程师，我想在矩阵之外看到总体不良率，以便和厂内目标值对照。
7. 作为质量负责人，我想按时间范围过滤热力图，以便区分「历史遗留」和「最近才开始出问题」。
8. 作为质量负责人，我想在热力图上一眼看出哪些测试项是定性项（外观检查、导通测试），以便知道这些格子的不良率含义与数值项不同。

### 下钻明细

9. 作为研发工程师，我想点击热力图的任一格子就在同一页展开明细，以便不打断我的思路去跳页。
10. 作为研发工程师，我想在明细里看到每条记录的三次测量值、平均值、规格、判定、批号、测试日期，以便完整复核判定过程。
11. 作为研发工程师，我想让三次测量中越界的那一次单独标红，以便看清是三次全坏还是只有一次坏。
12. 作为研发工程师，我想知道一条记录的判定依据是哪条判定规则（比如「min，阈值 20，单位 dB」），以便确认系统读懂了规格。
13. 作为研发工程师，我想在明细里点某条记录直接跳到它所属批次的录入网格，以便立刻修正录错的数。
14. 作为研发工程师，我想在明细为空时看到「该产品未配置此测试项」而不是一张空表，以便区分「无数据」和「不适用」。

### 批次录入网格

15. 作为研发工程师，我想选定产品和批号后，系统按该产品的测试模板自动铺出全部测试项行，以便不用手动决定这批要测什么。
16. 作为研发工程师，我想在网格里用 Tab 横向、Enter 纵向、方向键任意方向走位，以便双手不离键盘完成整批录入。
17. 作为研发工程师，我想从 Excel 复制一块区域直接粘贴进网格，以便把已有的电子记录一次导入。
18. 作为研发工程师，我想每填完一行就立刻看到该行的平均值和判定，以便当场发现异常值而不是保存后才知道。
19. 作为研发工程师，我想整批一次性保存，以便一个批次对应一次提交、一次成功或失败，不出现「录了一半」的中间状态。
20. 作为研发工程师，我想在保存前看到本批次的判定摘要（合格 X 项 / 不合格 Y 项 / 未判定 Z 项），以便确认没有漏填。
21. 作为研发工程师，我想让 `0` 被当成合法测量值保存，以便不再出现「填了 0 却存成空」的情况。
22. 作为研发工程师，我想让某项只填了一两次测量时也能保存并按已填的值判定，以便应对现场只做了部分测量的情况。
23. 作为研发工程师，我想让某项完全不填时保持「未判定」而不是被判成不合格，以便未测的项不污染不良率。
24. 作为研发工程师，我想编辑一个已存在的批次时网格直接带出原有数据，以便修正而不是重录。
25. 作为研发工程师，我想在离开未保存的网格时收到提醒，以便不会丢掉刚录的一屏数据。

### 判定引擎

26. 作为研发工程师，我想让 `≤0.5Ω`、`≥1500V`、`2.8±0.2mm`、`5.0~5.5mm`、`合格` 五类规格都被正确识别，以便覆盖我实际会写的全部形态。
27. 作为研发工程师，我想让 `≥1.5mm2` 的阈值被读成 `1.5` 而不是 `1.52`，以便单位里带数字时判定依然正确。
28. 作为研发工程师，我想让 `≥10^8Ω` 这类系统读不准的规格被明确标为「无法识别」并拒绝自动判定，以便我知道要人工确认，而不是拿到一个静默的错判。
29. 作为研发工程师，我想让判定规则以「类型 + 阈值 + 单位」的形式显示出来，以便我能核对系统是否读懂了我写的规格。
30. 作为研发工程师，我想让数值项按「三次测量是否全部落在规格内」判定，以便一次越界就算不合格，符合质检惯例。
31. 作为研发工程师，我想让定性项（规格为「合格」）由人工选择判定结果，以便系统不去猜外观检查的结论。
32. 作为质量负责人，我想让不良率的分母只统计已判定的记录，以便未判定项不把不良率稀释成假的好看数字。

### 产品与测试模板

33. 作为研发工程师，我想维护产品列表（型号、名称、图纸编号、说明），以便所有记录都挂在正确的产品上。
34. 作为研发工程师，我想维护每个产品的测试模板（测试项、规格、排序），以便批次录入时铺出正确的行。
35. 作为研发工程师，我想在编辑模板时立刻看到每条规格被解析成什么判定规则，以便在录数据之前就发现规格写错了。
36. 作为研发工程师，我想把一个产品的测试模板整体复制到另一个产品，以便新增相似型号时不用重录十几行。
37. 作为研发工程师，我想删除产品时同时清掉它的测试台账、模板等关联数据，以便不留下查不到归属的孤儿记录。
38. 作为研发工程师，我想在删除产品前看到将被一并删除的数据条数，以便确认这是我想要的。

### 两种数据来源

39. 作为评估者，我想直接打开一个在线链接就看到带真实数据的完整界面，以便不用 clone 代码就能判断这系统好不好用。
40. 作为评估者，我想在演示模式下清楚看到「数据不持久」的标注，以便不误以为我录的东西被保存了。
41. 作为评估者，我想在演示模式下也能完整走通「热力图 → 下钻 → 录入 → 判定」的闭环，以便评估的是真实体验而非静态截图。
42. 作为研发工程师，我想在本地运行时数据落到 SQLite 文件，以便这是我真正的工作数据。
43. 作为研发工程师，我想让本地模式和演示模式的界面与行为完全一致，以便演示里看到的就是我会得到的。

### 交互质量（针对 1.0 的「像模板」）

44. 作为研发工程师，我想让主要操作在同一页内完成而不整页跳转，以便保持上下文。
45. 作为研发工程师，我想让所有能点的东西都真的有反应，以便不出现「点了没反应也不知道为什么」的按钮。
46. 作为研发工程师，我想让加载中、空数据、出错三种状态各有明确的界面表现，以便不把「还在加载」误认为「没有数据」。
47. 作为研发工程师，我想让写操作失败时收到明确的错误信息，以便知道数据没存进去。

## Implementation Decisions

### 分层与模块

自上而下三层，依赖方向单向向下：

| 层 | 职责 | 依赖 |
|---|---|---|
| UI 层 | React 组件：热力图、下钻明细、录入网格、产品与模板管理 | 只依赖 `DataPort` 接口与领域核心 |
| 数据端口层 | `DataPort` 接口 + 两个适配器（`HttpAdapter` / `MemoryAdapter`） | 领域核心 |
| 领域核心 | 纯函数：规格解析、判定、不良率与热力图聚合 | 无（零 I/O、零框架） |

领域核心**不允许**引入任何 I/O、DOM 或框架依赖。这是双适配器能共用它的前提（ADR 0002）。

### 领域核心的对外形状

判定规则的类型定义来自 ADR 0004，此处不重复。原型已验证的解析器契约（保留这段是因为它把决策
编码得比散文更精确，来自 `prototype/ledger-ui.PROTOTYPE.html`）：

```ts
// 数值段只允许匹配 -?\d+(\.\d+)? ，紧随其后的剩余部分整体视为单位。
// 关键点：绝不用「剥掉非数字字符」的方式取数，那是 1.0 版静默错判的根因。
parseSpec(raw: string): JudgmentRule | { kind: 'unparseable'; raw: string }

// 单位段以 ^ / e / E / × / * 开头时判为 unparseable（ADR 0004 规则五）
```

判定与聚合：

```ts
// 数值项：三次测量必须全部落在规格内才算合格；已填的值不足三次时按已填的判。
// 全未填 → 'unjudged'（不进入不良率分母）。规格无法解析 → 'unparseable'（同样不进分母，且 UI 必须显式提示）。
judge(rule, values: (number | null)[]): 'pass' | 'fail' | 'unjudged' | 'unparseable'

// 单值越界判断，供 UI 只标红越界的那一次测量，而不是整行含糊标红
isValueOutOfSpec(rule, value: number): boolean

// 热力图聚合：测试项 × 产品 → 不良率 + 分母。分母只计已判定记录（对应故事 32）
buildHeatmap(records, templates): HeatmapMatrix
```

`0` 必须是合法测量值。空值只能由 `null` 表示，禁止用 `falsy` 判断区分（1.0 版
`parseFloat(v) || null` 是既有 bug 的来源）。

### DataPort 接口

一个接口，两个实现，方法集刻意保持最小：

- 产品：列表、单个、创建、更新、删除（删除返回将被级联清除的关联条数）
- 测试模板：按产品读取、整表替换、跨产品复制
- 测试台账：按产品与测试项查询（供下钻）、按批次读取、整批写入（供网格）、删除批次
- 聚合：热力图数据

**整批写入是原子的**：一个批次的全部测试项要么全部成功，要么全部失败，
不允许出现半保存状态（对应故事 19）。`HttpAdapter` 侧由 SQLite 事务保证。

所有跨边界数据用 Zod schema 校验，前后端共用同一份定义。
`HttpAdapter` 的响应必须过一次解析后才交给 UI —— 1.0 版
`/api/ledger/batches` 返回结构与前端预期不符却无人察觉，就是因为边界上什么都不校验。

### 后端与持久化

Hono + better-sqlite3，沿用 1.0 的 SQLite 单文件方案（ADR 0001）。
**`PRAGMA foreign_keys = ON` 必须在建立连接时立即执行**并有测试覆盖 ——
1.0 版漏了这一句，导致删除产品后留下孤儿记录（对应故事 37）。

表结构沿用 1.0 的核心部分（产品、测试台账、测试模板），字段名保持一致以便迁移；
外键约束补齐并加上 `ON DELETE CASCADE`。

**测量值列的存储类型**：三次测量与平均值存 `REAL` 且允许 `NULL`，
`NULL` 表示未填，`0` 表示测得 0。判定结果与判定规则类型独立成列，便于聚合查询时不必重新解析规格。

### 路由与信息架构

单页应用，URL 反映状态而不是页面：

- 首页 = 热力图；被选中的格子进入 URL（产品 + 测试项），刷新后保持展开
- 批次录入 = 独立路由（产品 + 批号），可从明细直接跳入
- 产品与模板管理 = 独立路由

**每个 API 端点只允许定义一次。** 1.0 版 `DELETE /api/ledger/batch` 被定义了 4 次、
`POST /api/templates/copy` 被定义了 2 次，是没有模块边界的直接后果。

### 适配器选择

构建产物读取环境变量决定默认适配器：本地开发与本地运行用 `HttpAdapter`，
GitHub Pages 构建用 `MemoryAdapter`。演示模式必须在界面上有持续可见的标注（对应故事 40）。
`MemoryAdapter` 的种子数据直接沿用 1.0 的真实数据（5 个产品、52 条模板项、6 个批次、62 条记录）。

## Testing Decisions

### 什么算好测试

只测**外部可观察行为**，不测实现细节。判定引擎的测试断言的是
「给定这条规格和这三个测量值，判定结果是什么」，不是「内部用了几个正则」。
解析器换实现但行为不变时，测试不应该需要改。

### 缝的位置（两道，都在尽可能高的位置）

**缝 1 — 领域核心（纯函数，零 I/O）**
主要测试重心。夹具直接取自现有 52 条真实规格串，逐条断言解析结果；
判定用真实的 62 条测试台账记录，断言与已知结论一致（RV-0.5 导体电阻 0.52 超 0.5、
SYV-75-5 回波损耗三次全低于 20dB、BV-2.5 老化测试 68% 低于 80%，总体不良率 4.84%）。

必须覆盖的回归用例：

- `≥1.5mm2` → 阈值 1.5（不是 1.52）
- `≥1.5 mm2`（带空格）→ 阈值 1.5
- `≥10^8Ω`、`≥1×10^8Ω` → `unparseable`，且判定拒绝给出结论
- `2.5mm2±0.1` → `unparseable`
- 测量值 `0` → 参与判定，不被当作未填
- 三次里只填一次 → 按一次判
- 三次全未填 → `unjudged`，不进不良率分母

**缝 2 — DataPort 接口（一套契约测试，跑两遍）**
针对接口而非实现写一套测试，分别对 `MemoryAdapter` 和 `HttpAdapter` 各跑一遍。
这直接保证「演示模式和本地模式行为一致」（对应故事 43），
也把 1.0 版「API 返回结构与前端预期不符」这类问题挡在边界上。

契约测试必须覆盖：整批写入的原子性（部分失败时不留残留）、
删除产品的级联清理（外键真的开着）、`0` 值往返不失真、查询空结果返回空集合而非 `undefined`。

**UI 层不设缝。** 不写 React 组件单测。理由：台账类应用的组件几乎全是表格渲染，
组件测试维护成本高而抓 bug 少；且本方案已把全部逻辑压到缝以下，组件里剩下的是纯呈现。
UI 的正确性靠原型阶段定形 + 实现后的人工走查（故事 44–47 逐条过）保证。

### 与 1.0 测试的关系

1.0 有一份 `workflow-test.js`（40 项端到端流程测试，全部通过）。
它的价值在于**功能清单**，而不是测试方式 —— 它测的是「跑得通」，
而本次的 76 个问题恰恰都是「跑得通但是错」。
因此不移植这份脚本，而是把它当作功能覆盖度的对照表：
2.0 落地时逐条核对「1.0 能做的这件事，2.0 做了没有」。

## Out of Scope

**本 spec 不含以下 1.0 已有功能**，它们留给后续 spec，并且在这些功能落地前
**1.0 版本必须保持可用（保留在 `legacy` 分支）**：

- BOM 与 BOM 明细管理
- 打样工艺记录与工艺参数
- 测试报告生成、签名、导出
- 测试台账的 CSV 导入 / 导出
- 全局搜索

这样切的理由：上面五项都依赖「产品 + 测试台账 + 判定」这个底座。
底座不牢时先把面积铺开，就是 1.0 憋出 76 个问题的原路。
先把核心闭环做到能真正日常使用，再逐个域迁移。

**明确不做的东西：**

- 用户与权限体系（单机自用工具，1.0 也没有）
- 规格改为结构化三字段录入（ADR 0004 已记为后续演进方向）
- 全局命令面板（原型变体 D 的想法，本次不引入，避免把败选变体的元素偷偷混进来）
- 移动端适配（工作场景是桌面 + 键盘）

## Further Notes

**关于变体 C 被选为主界面。** 原型评审时我推荐的是变体 A（批次工作台），
理由是「录入是最高频操作，该摆在正中间」。选择 C 意味着一个不同的判断：
这是**研发管理**系统，不是产线录入终端 —— 第一屏应该回答「现在哪里有问题」，
录入是顺着问题钻进去之后的动作。这个判断改变了信息架构的组织方式：
录入网格从「主界面」降为「从明细进入的工作区」，因此故事 13（明细直达录入）
是把两者接起来的关键一环，不能省。

**关于 1.0 那 76 个问题。** 它们不是本 spec 要逐条修的清单。
它们是诊断依据 —— 本 spec 的分层、缝的位置、Zod 边界校验、外键、
`0` 值处理，都是针对其中成因最集中的几类。
一份「先实现完再全面审计」的流程会再生产一批同类问题，
所以本次的应对是流程性的，不是逐条打补丁。

**关于原型的处置。** `prototype/ledger-ui.PROTOTYPE.html` 是一次性产物。
变体 C 的结构被本 spec 吸收后，该文件应删除，不进入 2.0 代码。
